  design-review-001）
- 対象: docs/design/opencode-v2-adapter-design.md（初版）

編集なしで設計書と上流資料を確認し、重要度順にレビューします。 設計書の前提（CLI・権限・委譲）を実環境と公式仕様で照合します。 スキル・コマンドの列挙可
否など、検証計画の前提をさらに確認します。

## レビュー結果（重要度順）

### 重大

**1. 前提・[問題] 方式 A（生成 config）は v2 の config 探索では起動できないまま G4 を満たせない** [根拠] §6.1 の
推奨理由(2)は「G4 を満たしやすい」だが、§6.3 は宛先を `<project>/.egm-opencode/` 等の任意ディレクトリに
`opencode.json` を生成する。v2 の公式 config 仕様では探索場所はシステム／グローバル（`~/.config/opencode`）／
プロジェクト（cwd→ルート探索）／`.opencode/` に固定され、`OPENCODE_CONFIG` 相当の外部指定は存在しない（
`--config` フラグも無い。`opencode <directory>` 引数を使うと cwd＝宛先になり、§4 の「ユーザー成果物はプロジェクト基
準」と衝突する）。本環境でも `OPENCODE_CONFIG=/tmp/nonexistent.json` の指定が無視されることを確認した。方式 B（プ
ラグイン）も `plugins` エントリは config ファイルへの登録が前提であり、G4 を回避できない。D4 を「確認事項」とする §5 は、本質的
には方式 A の存廃そのものを先送りしている。 [改善案] Phase 0 の go/no-go 関門に D4 を追加し、候補起動経路（プロジェクト配置、グ
ローバル配置、`OPENCODE_DISABLE_PROJECT_CONFIG=1` 併用、`opencode <directory>`）を実測比較すること。
G4 を「既存設定を暗黙に書き換えない（明示的オプトインのインストール手順で 1 ファイル追加する等）」に定義し直し、生成先を「探索される場所」に限定するか、
A 自体を再検討すること。

**2. 前提・[問題] §6.4 の権限写像は v2 の権限モデル（順序付きリスト・最終一致勝ち・基本 `* allow`）と不整合** [根拠] v2
の権限は辞書ではなく順序付き `{action, resource, effect}` リストで「最後に一致した規則が勝つ」。全エージェントの基本ポリシーは
`* allow`＋`.env` 系 `ask` であり、V1 の「`*` deny 先頭」のまま写像すると、列挙していないアクションが基本ポリシーの
allow で通る。さらに v2 では (a) MCP リソースは専用アクション `opencode_read_mcp_resource` /
`opencode_list_mcp_resources` であり、`read` への `mcp:*` deny（§6.4）は無意味、(b) `edit`
が edit/write/patch を兼ね（「書き込み deny」との列挙が曖昧）、(c) ネットワークは `webfetch`/`websearch`
に加え Code Mode の `execute`（内部 `fetch` を含む）が別アクションで、(d) `external_directory` の
resource は通常 `/*` 境界で V1 の `{bundle}/**` と形式が異なる、(e) `grep` の resource は検索正規表現
でありパスではない（deny 全体は正しいが根拠付けが逆）。 [改善案] §6.4 を v2 アクション全列挙（`read, glob, grep,
edit, shell, subagent, skill, question, webfetch, websearch,
experimental_image_generate, external_directory, execute, opencode_*_mcp_*,
<server>_<tool>`）＋「`* deny` 先頭、その後に read/glob allow、例外は末尾」の順序で書式化し、生成物の静的検査を「実
効リストの順序検証」にすること。MCP 対応を再定義すること。

**3. 権限設計の不備・[問題] マージ順により利用者設定が EGM の deny を上書きできるが、防御手段が検証時のクリーン環境のみ** [根拠] 権
限ルールは config 順に append され、プロジェクト／グローバル config の同 ID エージェント定義は同一リストに追記される。利用者の近
い階層の設定が EGM の deny の後に allow を足すと最終判定は allow になる。§12 の対策は「クリーンなプロファイルと使い捨てプロジェ
クトで検証」「debug で毎回検査」であり、利用者環境での耐性は無い。G3 の「権限レベルで拒否する」はこの条件の下では保証できない。 [改善案] 代替案
として (a) `policies`（`tool.use` の hard-deny。グローバル／システム policy はプロジェクト config より優
先）による防御、(b) 設置先をシステム config（`/etc/opencode`、要管理者権限）にするか、(c) 「保証はクリーン環境のみ。debug
agents の実効リストが想定通りでなければ起動拒否（ラッパースクリプト）」のいずれかを明示し、G3 の主張範囲を縮めること。

**4. Goldfish 分離の穴・[問題] L2（指示ファイル）は v2 アーキテクチャ上はレビュアー側で排除手段が無い等しい設計が §6.4/§7 に
無い** [根拠] v2 公式仕様でエージェント指定は「プロンプトを置換するが、プロジェクト指示・スキル・参照・その他の指示ソースは依然追加される」と明記。
これが Claude の `omitClaudeMd` や Copilot の `include-custom-instructions: false` に
相当する排除手段を持たないことを意味する。さらに v2 は `AGENTS.md`（グローバル＋cwd→ホームの全階層）を初期注入し、**対象ディレクトリを
読むと入れ子の `AGENTS.md` を動的に追加注入**する。§7.3 は L2 の除外手段が無い場合を「制限として明示」で処理するのみで、§6.4 の
権限設計にも指示ファイル対策が無い。Goldfish 設計の核心である独立性を、既知の漏洩を許容したまま「支持」にできる構造である。 [改善案] ① 使い捨
てプロジェクト（AGENTS.md 無し）を正とする運用を標準手順化、② `-代`案として `references`/外部ディレクトリ経由の読み取りや対象コ
ピー手順を検討、③ 排除手段が無い場合は支持主張を「親ターン分離のみ（host-instruction leak 既知）」と名指しで限定し、README や
支持表記に漏洩を明記すること。

### 中

**5. 前提・[問題] §7.3 の分離検証が「マーカー不在＝分離の証明」になりがちで証跡として弱い** [根拠] 上流
`docs/opencode.md` の verifier 制限に「親の要約やマーカー不在を分離証跡として十分扱うな」と明記されている。§7.3 は子
export と出力の不在確認を主とし、ポジティブ証跡（子が注入された指示セクションの検査、必須 read の完了記録、親子セッション ID の対応、§10
層 3 手順 4 の「子の有効権限の検査」）が手順として未指定である。 [改善案] マーカー不一致に加え、子セッション export における (a) 実行
記録内の AGENTS.md 由来のエントリ有無、(b) 必須パスの read 完了、(c) `debug agents` の実効権限 JSON の保存を必
須化すること。失敗パターンを上流 verifier 相当（開始・完了・時刻・レビュー種別・tool call の session ID 対応）に揃えること。

**6. 検証計画の不十分・[問題] 層 1 の `debug config`/`debug agents` で「スキル 7 件・コマンド 7 件が列挙され
る」とできていない** [根拠] v2.2.6 の `debug` サブコマンドは `agents / config / paths /
heap-dump` のみで、スキル・コマンドの列挙手段が無い。実測でも `debug config` は providers と directory のみ
を返し、`debug agents` は全ビルトインを含むため「エージェント 9 件」の数え方も不定義。スキル ID がパス由来（frontmatter
`name` は表示名のみ）である点も §6.3 に未反映で、V1 の `skills.paths` オブジェクト形式は v2 の配列形式 `skills:
[...]`（相対パスは config ファイルではなく cwd 基準）と異なる。 [改善案] 静的検査（生成 `opencode.json` のパース、ス
キル配置の実在確認、ID 一致確認）と `debug agents`（EGM ID フィルタでの実効権限ダンプ）に置き換え、絶対パスの使用を明記すること。

**7. 検証計画・支持主張の条件が §3-F6 自身の前提より弱い** [根拠] F6 は「マニフェスト追加とハーネス文書の更新も求められる」と記すが、
§10 の支持条件は層 1＋層 3＋L1 のみで、ハーネス文書（README のみでは無い）も、上流 `additional-harnesses.md` の
「skill テストシナリオ（brainstorm/draft/review の test_scenarios.yaml）の再利用」も含まない。また L2
が未達でも「制限として併記」のみで「OpenCode v2 対応」と称しうる構造であり、結論のスコープ（テスト済みモデル・surface・host バージョ
ンへの限定）も §10 に明文化されていない。 [改善案] 支持条件にハーネス文書・テストシナリオ再利用・検証記録の公開を含め、支持文を「テスト済みホスト/
モデル/surface に限定し、L2 未検証なら『親ターン分離のみ検証済み』」と呼称すること。

**8. 楽観的な仮定・[問題] 生成器が TypeScript＋Bun/Node 前提だが、実行・配布経路が設計に無い** [根拠] V1 の
`install.py` は Python 標準ライブラリのみの単一ファイルで、実行環境の前提が小さい。§6.2 の `generate.ts` は「
OpenCode が前提とする Bun/Node を使う」と述べるのみで、利用者が生成器をどう取得・実行するか（npm パッケージか、`bun run` か、
事前ビルド bundle か）が未定義。Bun を持たない利用者には導入できない。 [改善案] 配布形態（Q1）を Phase 0 ではなく設計段で決め、
(a) Python 標準ライブラリ生成器の再利用、(b) 事前生成済み bundle＋ハッシュ配布、(c) npm パッケージ配布 のいずれかで、実行前提
と失敗時挙動を明記すること。

**9. 権限設計の不備・[問題] コマンドのシェルマーカー展開が「v2 前処理仕様の確認」止まりで、生成物側の運用規定が無い** [根拠] v2 のコマン
ド仕様でも ``!`...` `` ブロックは権限フロー外で実行される。`/egm-review` 等は引数に生テキストを渡す入口であり、§8・§12 の「
ファイル経由を標準手順」は願望止まりで、テンプレート設計（パスだけ許容、引用符付き引数の扱い、ペイロード検査）が無い。 [改善案] コマンドテンプレートの引
数を「既存ファイルの絶対パスのみ」とし、引数に ``!` `` 等を含む場合は primary 側で拒否・停止する規定を生成物（プロンプト／生成器バリデーシ
ョン）に落とし込むこと。未信頼素材の slash 引数禁止を README とコマンド説明に明記すること。

**10. 不整合・[問題] Phase 0 の go/no-go 関門が D1/D2 のみで、D4/D5 の不成立を扱わない** [根拠] §11 は
go/no-go を「D1 と D2 の成立」に限定しているが、D4（設定分離）が不成立なら方式 A そのものが崩れ、D5（トレース取得）が不成立なら層
2/3 の verifier が作れない。関門が不完全。 [改善案] D3–D5 にも関門条件と不成立時のフォールバック（B/C への移行、verifier
の代替証跡、支持主張の取り下げ）を定義すること。

**11. 抜けている代替案・リスク・[問題] `installation.json` が生成物 config 自体をハッシュ化せず、移動・改変の検出ができ
ない** [根拠] V1 の `install.py` は `bundle` 配下のファイルのみをハッシュ化し、`opencode.json`（権限定義を含
む）とスキルエイリアスは含まない。§6.3/G5 の「全同梱ファイル」も同じ範囲であり、生成物 config の改変（allow の追加等）が検出できない。
また bundle 移動時の禁止（絶対パス埋め込みと上書き注意）は利用者への明記が無い。 [改善案] マニフェストに生成済み `opencode.json`
とスキルエイリアスの目標を含むこと。移動禁止と、再生成時のアトミック置換／上書き拒否の扱いを明記すること。

### 軽微

**12. 前提の細部・[問題] F7/G2 の「AGENTS.md 等」と `CLAUDE.md` の並記** [根拠] v2 は `AGENTS.md`
のみを認識し、`CLAUDE.md` はフォールバックしない（公式 instructions 仕様）。「等」の射程が曖昧。 [改善案] L2 の対象を「
AGENTS.md（グローバル・プロジェクト・入れ子の動的注入、config `instructions` の glob/URL）」に再定義すること。

**13. 前提の細部・[問題] D6（質問ツール）を未確認事項としているが、公式 v2 仕様に既に `question` ツールと `question`
権限アクションが存在する** [根拠] tools/permissions 仕様で確認可能であり、Phase 0 での実測項目から外せる。 [改善案]
`question` ツールを用いる設計に確定し、平文フォールバックは「ツールが拒否された場合」に限定すること。

**14. 運用規定の欠落・[問題] `opencode run --auto`（ask 既定承認）と、レビュー実行コストへの言及が無い** [根拠]
`--auto` は「明示的に deny されていない権限を自動承認」し、primary の `ask` 基本を無力化する（検証時の承認ゲート確認も汚染する）。
また review は 5 フェーズ×最大 8 名の子セッションで、§12 のリスク表にコスト・`steps` 上限が無い。 [改善案] 検証・配布手順で
`--auto` 使用を禁止し、必要なら自動承認に耐える設計（primary も `ask` を維持）であることを注記すること。コストは `steps` 上
限・モデル選択の指針で扱うこと。

**15. 細部・[問題] F1 の根拠が単一事例（botid プラグイン）で、API の出典がトレーサブルでない。§6.3 の宛先チェックも V1 の「ソー
スツリー内へのインストール禁止」や宛先シンボリックリンク自体の拒否が欠けている** [改善案] F1 に対応するプラグイン実装の所在（ファイル・版）を記録す
ること。宛先検証に上記 2 項目を復元すること。

### 良い点

- F7 のような上流の実例（#237）に基づき L1/L2 を分離し、L2 未達を「支持主張の範囲から外す」方針を §7.3・§10 に一貫して書き込んだ
  点は妥当である。
- 「設定したこと」と「強制したこと」を §6.4 で区別し、層 1–3 で証跡の粒度を切り分けた点、`.env` 系（`.env.example` の
  allow を含む）や `grep` 迂回など V1 の知見を落としていない点は良い。
- §12 のリスク表に「コマンド引数のシェルマーカー展開」「config マージ汚染」「vendor 陳腐化」まで手を伸ばしており、N3・N4 の境界（還
  流・委譲対象外の扱い）も明確である。
