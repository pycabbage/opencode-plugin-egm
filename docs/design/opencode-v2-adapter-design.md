## 1. 背景と目的

EGM は「文脈を持つ Elephant が仕様を起草し、文脈を持たない Goldfish が
レビューし、人間が承認する」ためのプラグインである。上流は OpenCode V1 向けの
実験的アダプタを持つが、OpenCode v2 はサポートしていない。V1 と v2 では
プラグイン API、委譲（delegation）インターフェース、権限（permission）
インターフェースが互換でなく、V1 アダプタの生成物はそのままでは v2 で動かない。

本設計の目的は、EGM の正典（canonical）なスキル・ペルソナ・リソースを
改変せずに、OpenCode v2 上で EGM ワークフローを実行できるアダプタを
このリポジトリ（pycabbage/opencode-plugin-egm）で提供することである。

## 2. ゴール / ノンゴール

### ゴール

- G1: `/egm-brainstorm`、`/egm-draft`、`/egm-review` がプラグイン導入経由で
  エンドツーエンドに動作する（上流 `docs/harnesses.md` の「supported」基準）。
- G2: Goldfish レビュアーの文脈が §7.2 の不変条件 1–3（文脈の構成、
  持ち越し禁止、自己完結した読み取り）を満たし、親の会話履歴を引き継がない
  ことを検証可能な形で示す。あわせて、ホスト指示ファイル（AGENTS.md 等）が
  レビュアーの文脈に入らないかを別個に検証し、結果を分けて報告する。
- G3: レビュアーは読み取り専用とする。書き込み・シェル・委譲・ネットワーク系
  ツールを権限レベルで拒否し、`*.env` 系ファイルの読み取りも拒否する。
  保証の範囲は §6.5 で限定する（検証済みの起動構成でのみ主張する）。
- G4: ユーザーの既存の OpenCode 設定をアダプタが **暗黙に** 書き換えない。
  設定の追加は、利用者が明示的に実行する導入手順の中で、v2 が探索する
  場所への配置としてのみ行う（§6.3）。既存ファイルの上書きはしない。
- G5: インストール内容を再現可能にする。同梱ファイルに加えて生成した
  設定ファイル自体も SHA-256 の記録対象とし、インストールマニフェストを
  生成する（§6.3）。

### ノンゴール

- N1: EGM のスキル・ペルソナ本文（上流の正典テキスト）の改変や翻訳。
- N2: OpenCode 本体へのパッチ。公開インターフェースの範囲で実装する。
- N3: 上流リポジトリへの PR 作成（上流 AGENTS.md が自律 PR を禁止している。
  還流する場合も人間の明示承認を前提とする）。
- N4: bootstrap オーケストレータ／スカウト、および synthesizer の委譲対応
  （V1 アダプタと同様に当面は対象外とし、必要になった時点で別途設計する）。
- N5: OpenCode v2 以外のホスト（Cursor、Copilot 等）への対応。

## 3. 前提と検証済み事実

以下は 2026-11-09 時点で、この開発環境（OpenCode v2.2.6）で実測した事実である。
推測とレビュアー報告は「未確認事項」として §5 と §13 に分離する。

- F1: OpenCode v2.2.6 のプラグインは `Plugin.define({ id, setup(ctx) })` 形式で
  ある。実例は botid プラグイン（`ctx.shell.hook("create.before", ...)` を使用し
  `ctx.location.directory` を参照）。この環境での所在は
  `~/.config/opencode/plugin/botid.ts`（botid v0.2.2 同梱物）で、動作を確認済み。
  ただしプラグイン API の全範囲の根拠としては単一事例であり、エージェント
  登録等の可否は D3 で別途確認する。
- F2: `opencode run` は `--model provider/model#variant`、`--agent`、
  `--session`、`--fork`、`--worktree`、`--archived`、`--format json` を持ち、
  セッションは `opencode session` で export/import できる。
  `--auto` は「明示的に deny されていない権限を自動承認」するため、
  承認ゲートの検証を汚染する。本アダプタの検証・配布手順では `--auto` の
  使用を禁止する。
- F3: `opencode debug` のサブコマンドは `agents`、`config`、`paths`、
  `heap-dump` のみである。スキルとコマンドを列挙する debug 手段は無い。
  `debug config` はマージ済み設定の内容を返し、`debug agents` はビルトインを
  含む全エージェントを返す。したがって層 1 検査は §10 の通り「生成物の静的
  検査＋ `debug agents` の EGM 分の実効ダンプ確認」に置く。
- F4: 上流 V1 アダプタは「生成 config 方式」である。インストーラ
  （`adapters/opencode/install.py`）が正典ツリー（skills/agents/resources/docs）
  を bundle にコピーし、`opencode.json` を生成する。内容は次の通り。
  - `default_agent: egm`、スキルは `skills.paths` とシンボリックリンクで公開
  - レビュアー 8 名を `mode: subagent` として登録し、権限は原則 deny、
    `read`（`*.env` 系 deny、`mcp:*` deny）と `glob` のみ allow、`grep` は
    read ルールを迂回するため deny、`external_directory` は bundle 内のみ allow
  - プライマリ `egm` は権限 `ask` を基本とし、`skill` は `egm-*` のみ、
    `task` はレビュアー 8 名のみ許可
  - コマンド 7 件は各スキルを `egm` エージェントに結び付け、テンプレートで
    正典 SKILL.md の絶対パスを渡す
- F5: V1 の委譲規約（`docs/opencode.md`）は次の通り。新規セッションで
  foreground 実行し、セッションを再利用しない。渡すのはタスク説明と
  ペルソナ・対象・標準文書の絶対パスのみで、親の履歴・推論・メモリは渡さない。
  委譲できなければレビューを模擬せず停止する。
- F6: 上流の支持基準は「プラグイン導入経由で /egm-brainstorm、/egm-draft、
  /egm-review がエンドツーエンドに動作すること」。マニフェスト追加と
  ハーネス文書の更新も求められる。本リポジトリ側の支持条件は §10 に定義する。
- F7: 分離の証跡は種類が別である。上流 issue #237 では、他ハーネスで
  「親ターンの分離は保たれたが、プロジェクト／ユーザーの AGENTS.md が
  レビュアー文脈に入った」事例が報告されている。会話履歴の分離と
  指示ファイルの除外は分けて検証・報告しなければならない。
- F8: V1 の検証資産は、(a) オフライン単体テスト（生成物の同一性と上書き拒否）、
  (b) スクリプト化されたローカルモデルによるネイティブプローブ（子セッション
  派遣、親マーカー、`.env` 読み取り拒否の確認）、(c) 親 JSONL トレースと
  子セッション export を突き合わせる trace verifier、の 3 層である。
- F9: v2.2.6 のサーバー API には `session.generate` という operation が存在し、
  sessionID を必須パラメータとする（実測: この環境で `opencode api` から
  確認し、存在しないセッション ID では SessionNotFound が返った）。
  それ以外の性質は未確認である。「セッションの文脈にプロンプトを載せて
  生成し、そのプロンプトと出力をセッションへ永続化しない」という性質は
  利用者からの説明であり、実測ではない。ツール実行と権限強制の有無、
  呼び出し記録の残り方を含め、D1 の候補として Phase 0 で実測する。

## 4. 上流 EGM の構造とハーネス依存点

- スキル 7 件（`skills/egm-*/SKILL.md`）: brainstorm、draft、review、
  review-loop、resolve、bootstrap、drift-report。v2 ではスキル ID は配置パス
  由来であり、frontmatter の `name` は表示名にすぎない（レビュー 001 指摘。
  Phase 0 で確認）。生成物では ID が正典名と一致するよう配置を設計する。
- ペルソナ 10 件（`agents/*.md`、frontmatter の `name` が `egm-*` 形式の正典名）。
  レビュアーは 8 名（codebase_details、comprehension、design_critic、
  implementation_readiness、inventive_catalyst、structural、style、zoom_out）。
  残り 2 件（bootstrap_orchestrator、synthesizer）は委譲対象外（N4）。
- リソース: `resources/document_standards/` と `resources/execution_instructions.md`。
  スキルは実行時に `agents/` と `resources/` を参照するため、スキル単体では
  動作しない。bundle 全体を一体として扱う必要がある。
- パス解決規約: bundle 相対物（agents/resources/docs）は bundle ルート基準、
  `references/` は正典スキルディレクトリ基準、ユーザー成果物はプロジェクト
  作業ディレクトリ基準。生成されるプロンプトには bundle ルートの絶対パスを
  埋め込む（V1 踏襲）。
- 承認ゲート: brainstorm→draft の合成（`concepts_brief.md`）、review の各
  ステージ報告ファイル、Step 8 前の `zoom_out_report.md` 存在確認など、
  正典スキルが定める停止条件と人間承認をアダプタ側で弱めてはならない。

## 5. V1 → v2 の差分と未確認事項

上流 `docs/opencode.md` は「V1 の `task` と `permission` インターフェースを
対象とし、v2 の `subagent` と `permissions` インターフェースは対象としない」
と明記している。以下は v2 で確認が必要な差分であり、§11 の Phase 0 で
すべて関門（go/no-go またはフォールバック）として扱う。

- D1: 委譲インターフェース。要件は §7.2 の不変条件であり、実現手段は
  次の 2 候補から Phase 0 の実測で選ぶ。
  - 候補 (a) サブエージェント派遣: v2 の派遣が「新規セッションを作る」
    「foreground で完了を待つ」「結果を親に返す」を満たすか。また
    セッション再利用を防ぐ指定方法があるか。
  - 候補 (b) `session.generate`（F9）: 専用の空文脈セッションをベースに
    生成する方式。採用条件は次の (i)–(iv) のすべてが実測で成立すること。
    - (i) ベース文脈を、親セッションの履歴を含まない最小構成にできる。
      不成立なら候補 (b) は不採用。
    - (ii) 通常のセッション実行と同等のツール実行と権限強制（§6.4）が
      効く。Elephant がファイル内容を読んで文脈に注入する形になる場合は
      不変条件 3 を満たさず不採用。実効確認は §6.4 のネガティブプローブ
      （書き込み、シェル、`.env` 読み取り、external_directory、MCP、委譲）
      で行う。
    - (iii) 呼び出し側にリクエストと結果の記録が残り、§7.4 の等価証跡
      （(b) 用 verifier の要件）を満たせる。不成立の場合、(b) の経路では
      §10 の支持条件を満たさないため支持主張を行わない。
    - (iv) 非永続化と呼び出し間の非漏洩が実測できる。1 回目の呼び出しに
      置いたマーカーとツール実行結果が、同じベースセッションへの
      2 回目の呼び出しの文脈・出力に現れないこと。
    あわせて次も確認する: プライマリからの呼び出し経路、実行主体となる
    エージェントと 8 ペルソナ・モデルの切り替え方法、複数回の read を
    含む反復実行、同期完了・タイムアウト・エラーの区別、ベースセッションの
    生成条件（空であること、親セッションからの fork でないこと、生成時の
    作業ディレクトリとプロファイル）、L2 の指示ファイル注入がどの時点で
    起こるか。
  - 候補 (a)(b) の双方が採用条件を満たす場合の選択基準は、優先順に
    (1) §6.4 の権限適合、(2) 証跡の完全性と verifier の実装容易性、
    (3) 実行コスト、とする。
- D2: 権限モデル。レビュー 001 によれば v2 の権限は順序付きルール列で
  「最後に一致した規則が勝ち」、全エージェントの基本ポリシーは緩い。
  F4 の権限マップは写像ではなく再設計が必要（§6.4）。Phase 0 では
  (a) ルールの順序意味論、(b) アクションの完全な列挙（MCP 専用アクション、
  Code Mode の `execute` 等を含む）、(c) 基本ポリシーの内容、を確認する。
- D3: エージェント／スキル／コマンドの登録経路。config への静的記述、
  マークダウンファイル配置、プラグイン API による動的登録のどれが v2 で
  公式に使えるか。スキルの公開方法（v1 の `skills.paths` 形式は v2 では
  配列形式で、相対パスの基準も異なる、とレビュー 001 は述べる）も含む。
- D4: 設定の配置と分離。レビュー 001 によれば v2 の config 探索場所は
  システム／グローバル／プロジェクト／`.opencode/` に固定され、
  `OPENCODE_CONFIG` 環境変数は効かない（レビュアーが本環境で確認したと
  述べる。スポットチェックでも `debug config` の出力は不変だった）。
  Phase 0 では次の候補経路を実測比較し、起動経路を 1 つに確定する。
  - (a) プロジェクトの `.opencode/` への配置（導入先プロジェクト限定）
  - (b) 専用プロファイルでの起動（`XDG_CONFIG_HOME` 等を候補ディレクトリに
    向け、ユーザーのプロジェクトを cwd のままにする）
  - (c) `opencode <directory>` で候補ディレクトリを cwd とする
    （成果物の解決基準がプロジェクトとずれる問題への対処が別途必要）
  - (d) プラグイン経由の登録（D3 の結果に依存）
- D5: トレース取得。v2 のセッション export（F2）が、trace verifier 相当の
  突き合わせ（親子セッション ID、ツール呼び出し、必須 read の完了）に
  足る情報を含むか。D1 で候補 (b) を選ぶ場合は、永続化されない生成の
  記録（サーバー側の記録または呼び出し側のリクエスト／レスポンス保存）が
  同等の証跡になるかも含めて確認する。
- D6: 質問ツール。レビュー 001 によれば v2 には `question` ツールと
  同名の権限アクションが存在する。本設計は `question` を使うことを既定とし、
  Phase 0 では存在確認のみ行う。ツールが使えない場合に限り平文の質問で
  停止する（V1 のフォールバック規約）。
- D7: 権限の上書き耐性。config のマージで利用者設定が EGM の deny の後に
  allow を足すと最終判定が変わりうる（レビュー 001 指摘）。対策候補として
  `policies` による hard-deny の可否と優先順位を Phase 0 で確認する。

## 6. 提案アーキテクチャ

### 6.1 方式の選択

| 方式 | 概要 | 長所 | 短所 |
| --- | --- | --- | --- |
| A. 生成・配置方式（V1 踏襲の改訂） | 生成器が bundle と v2 形式の設定を生成し、D4 で確定した探索される場所へ配置する | 上流の検証資産（単体テスト、プローブ、verifier の考え方）を流用できる。配置は明示手順に閉じる（G4） | 起動経路が D4 の実測結果に依存する。配置先がプロジェクト内の場合はプロジェクトごとの導入になる |
| B. プラグイン方式 | `Plugin.define` のプラグインが setup 時にエージェント等を登録し、資産を同梱する | 導入が 1 手順になる可能性がある | D3 次第で登録できる範囲が不足する可能性。動的登録はオフライン検証しにくい。プラグイン登録自体も config への追記を要し G4 を自動的には満たさない |
| C. プロジェクトテンプレート方式 | `.opencode/` 以下のファイル一式をプロジェクトにコピーする素材として配る | 単純で透過的 | プロジェクトごとに複製され、更新とハッシュ検証（G5）が弱い |

推奨: **A を基本方式とする。** 理由は、(1) V1 で実績があり上流の検証思想を
そのまま引き継げる、(2) G4・G5 を満たしやすい、(3) D1–D7 の不確実性が
「生成物の静的検査」として切り分けられる、の 3 点である。
B は Phase 0 の結果次第で「生成済み設定を読み込ませるだけの薄いランチャー」
として再評価する。エージェント登録そのものを動的に行う設計は現時点では
採用しない。

### 6.2 リポジトリ構成案と配布形態

配布形態は設計段階で確定する（レビュー 001 指摘 8 への対応）。

- 生成器は **Python 3 標準ライブラリのみの単一ファイル** とする
  （`install.py`。V1 の前提の小ささを踏襲し、利用者に Bun/Node の
  追加前提を課さない）。生成器の取得は本リポジトリの clone または
  リリース添付ファイルとする。
- 上流 EGM 資産は固定スナップショットとして同梱し、取得元コミットと
  ハッシュを記録する（`vendor/egm/`。正典は改変しない）。
- リリース物は `install.py` 単体ではなく、`install.py` と `vendor/` を
  まとめたアーカイブ（tar.gz）とし、アーカイブ自体の SHA-256 を公開する。
  `install.py` のみの単体配布は行わない（vendor が欠けた導入手順は定義しない）。
- 実行前提は Python 3.10+ と POSIX シンボリックリンク（V1 と同じ）。
  前提を満たさない環境では生成器は理由を表示して停止する。

```text
opencode-plugin-egm/
  docs/design/            本設計とレビュー記録
  install.py              生成・配置を行う単一ファイル生成器（§6.3）
  vendor/egm/             上流 EGM の固定スナップショット
  tests/
    unit/                 生成物の同一性、上書き拒否、権限リストの検査
    probe/                ローカルモデルによるネイティブプローブ（v2 版）
    verifier/             親トレース×子 export の突き合わせ（v2 版）
  README.md               導入手順、対応表、検証状況、既知の制限
```

### 6.3 生成物と配置

生成器は宛先ディレクトリを新規作成し（既存パスへの上書きは拒否する）、
次を生成する。生成物の配置先（v2 が探索する場所への置き方）は D4 の
確定結果に従い、導入手順として README に明記する。

- `bundle/`: 上流正典ツリー（skills、agents、resources、docs）のコピーと
  `plugin.json`、`LICENSE`、`README.md`、`TESTING.md`
- `skills/`: 正典スキルへのエイリアス（シンボリックリンク。POSIX 前提）
- v2 形式の設定ファイル: 少なくとも次を含む。
  - プライマリエージェント `egm`（F4 のプロンプト規約を v2 の書式で再記述）
  - レビュアー 8 名のサブエージェント定義と §6.4 の権限
  - スキル公開設定とコマンド 7 件（各スキルを `egm` に結び付ける）
  - 既定エージェントの指定方法は D4 の確認結果に従う
- `installation.json`: 上流名・バージョン、対象ホストバージョン、
  状態（experimental）、同梱ファイルに **生成した設定ファイルとスキル
  エイリアスのリンク先を含めた** 全ファイルの SHA-256。
  `installation.json` 自身は自己参照になるためハッシュ対象から除外する。
  生成する設定ファイルの名前は `opencode.json` を既定とし、D4 の確定結果に
  従って配置場所とともに最終決定する

パス検証は V1 踏襲に次を加える。宛先パスにテンプレート／glob 特殊文字を
含む場合、`.env.` を含む場合、宛先自体がシンボリックリンクの場合、
ソースツリー内部への生成は、いずれも拒否する。
生成物は絶対パスを埋め込むため **インストール後の移動は禁止** とし、
README に明記する。再配置は新規宛先への再生成でのみ行う。

### 6.4 権限設計

前提: v2 の権限は順序付きルール列であり最終一致が勝つ（D2、Phase 0 で確定）。
レビュアー（Goldfish）の権限は F4 の意図を v2 の書式で再設計する。

- ルール列は「`*` に対する deny を先頭に置き、その後に許可する read/glob を
  定義し、例外は末尾に置く」順序で生成する。列挙していないアクションが
  基本ポリシーで通ることがないよう、アクションは Phase 0 で確定した
  v2 の全列挙（少なくとも `read`、`glob`、`grep`、`edit`、`shell`、
  サブエージェント派遣、 `skill`、`question`、`webfetch`、`websearch`、
  `external_directory`、Code Mode の `execute`、MCP 専用アクション
  （リソース読み取り／一覧）、各 MCP サーバーのツール）を対象に棚卸しする。
- `read` はパス別に `*.env`、`*.env.*` を deny し、`*.env.example` は allow。
  MCP リソースの読み取りは v1 の `read` への `mcp:*` 写像ではなく、
  v2 の専用アクションで deny する。
- `grep` は deny。内容検索が per-file の read ルールを迂回しうるため
  （resource が正規表現である点も含め、検索経路自体を閉じる）。
- `edit` は write/patch を兼ねるため、書き込み系は `edit` の deny で代表させ、
  生成物の静的検査で同義の別名が漏れていないか確認する。
- `external_directory` の resource 表記は v2 の境界形式（`/*` 等）に合わせ、
  bundle 内のみ allow、それ以外は deny を原則とする。ただしレビュアーは
  bundle 外の対象文書と必須 prior report を読めなければならないため、
  `read` と `external_directory` の相互作用を Phase 0 で確認し、生成時に
  「対象文書と prior report の絶対パス（ファイル単位）」を許可リストへ
  追加する形で両立させる。ディレクトリ単位の広い allow は行わない。
- 書き込み、編集、シェル、ネットワーク、スキル、委譲はすべて deny。
- プライマリ `egm` は `ask` を基本とし、`skill` は `egm-*` のみ、
  委譲はレビュアー 8 名のみ許可する。合成と報告の書き込みはプライマリが行う。
  承認ゲートは `question` ツールで行う（D6）。
- 静的検査は「実効ルール列の順序と最終一致の結果」を対象とする。
  `debug agents` で得た EGM エージェントの実効権限ダンプを保存し、
  想定リストと機械的に突き合わせる。

### 6.5 権限保証の範囲と起動前検査

- G3 の保証は **検証済みの起動構成でのみ** 主張する。利用者設定との
  マージで実効権限が変わりうること（D7）は README に既知の制限として
  明記する。
- D1 で候補 (b) を採用する場合、この照合は必要条件であって十分条件では
  ない。`debug agents` のダンプはエージェント定義の実効権限を示すが、
  generate 経路で実際にそのエージェントが実行主体になり権限が効くかは、
  D1 (ii) のネガティブプローブで別途確認する。
- 起動ラッパー（導入手順に含める小さなスクリプト）は、起動前に
  `debug agents` の実効権限ダンプを想定リストと照合し、不一致なら
  理由を表示して起動を拒否する。これにより「マージで汚染された状態で
  レビューが走る」ことを防ぐ。基本ポリシー由来の allow をこの照合で
  検出できるかどうかも Phase 0 の確認項目とする。
- G3 の保証は **ラッパー経由の起動の場合に限る**。ラッパーを経由しない
  直接起動は未保証であることを README に明記する。
- D7（`policies` の hard-deny）が利用可能と確認できれば、レビュアーの
  deny は `policies` を主手段とし、ルール列は補助とする（Phase 1 で確定）。

### 6.6 コマンド引数の安全規約

- コマンドテンプレートの引数は **既存ファイルの絶対パスのみ** とする。
  レビュー素材の本文をスラッシュコマンド引数に貼る手順は提供しない
  （v1/v2 ともコマンド前処理でシェルマーカーが権限フロー外で評価される
  既知の問題への対処）。
- 引数にシェルマーカー（``!` `` で始まるブロック等）や引用符による
  埋め込みが検出された場合、プライマリは実行せず停止し、ファイル経由の
  提示を案内する。この規定は生成するプロンプトとコマンド説明文に明記する。
- 未信頼素材はファイルに保存してからパスで渡すことを README の標準手順
  とする。
- なお、シェルマーカーの展開はコマンド前処理で起こるため、プライマリの
  停止判断では原理的に防ぎきれない。そこでレビューの標準入力経路は
  スラッシュコマンドではなく、V1 アダプタの案内と同様に「`egm` エージェント
  への通常メッセージでファイルパスを渡す」形を標準とし、スラッシュコマンドは
  信頼できる呼び出し（パスだけの引数）に限る。残存リスクは README に明記する。

## 7. Goldfish 分離設計

### 7.1 分離の定義（3 層）

- L1 親ターンの分離: レビュアーの文脈に親セッションの会話履歴・推論・
  メモリが入らない。
- L2 指示ファイルの分離: レビュアーの文脈に指示ファイルが自動で入らない。
  対象は AGENTS.md（グローバル、プロジェクト、対象ディレクトリ配下の
  入れ子の動的注入）と、config の `instructions` で読み込まれる glob/URL
  とする。レビュー 001 によれば v2 は CLAUDE.md をフォールバックとして
  読まない（Phase 0 で確認）。L1 とは独立に検証する（F7）。
- L3 間接漏洩の防止: 共有ファイル経由の漏洩を避ける。レビュアーに渡すのは
  対象文書、標準文書、段階上必要な prior report の絶対パスのみとし、
  それ以外の成果物ディレクトリ探索を促さない。

### 7.2 派遣規約

要件は手段ではなく不変条件である。

- 不変条件 1（文脈の構成）: レビュアーの文脈は「タスク指示文、ペルソナ、
  対象、標準文書、段階固有の必須 prior report（必要な場合のみ）」だけで
  構成され、親セッションの会話履歴・推論・メモリを含まない。タスク指示文
  に対象等の要約や親の見解を混ぜないことは不変条件 1 の一部である。
- 不変条件 2（持ち越し禁止）: レビューの間、および review のフェーズ間で、
  文脈を持ち越さない。前段の結果は prior report として明示的に渡された
  場合にのみ参照できる。
- 不変条件 3（自己完結した読み取り）: レビュアーは §6.4 の権限制御の下で
  自分でファイルを読む。呼び出し側がファイル内容を読んで文脈に注入する
  方式は、この不変条件を満たさない。

実現手段は D1 の候補 (a) サブエージェント派遣 / 候補 (b) `session.generate`
から Phase 0 で選ぶ。いずれの手段でも次を守る。

- (a) の場合: レビュアーは毎回新規セッションで起動し、セッション ID を
  指定した再開や使い回しをしない（V1 の `task_id` 省略に相当）。
- (b) の場合: ベースにするセッションは親セッションとは別の専用セッション
  とし、**派遣ごとに新規に作る** ことを原則とする（親からの fork は禁止。
  生成条件は D1 で確定する）。非永続化の性質は F9 の通り未確認であり、
  不変条件 2 の根拠にするには D1 (iv) の実測が前提になる。ベース文脈
  自体の構成（不変条件 1）とツール・権限（不変条件 3）も実測で確認する。
  派遣ごとの新規作成ができない場合に限り再利用を検討するが、その場合は
  D1 (iv) の呼び出し間リーク検査に合格することを必須とし、ベース
  セッションに残るツール結果等の扱いを設計に明記する。
- foreground で完了を待ち、バックグラウンド派遣は使わない。
- プロンプトには対象等の絶対パスだけを含め、内容の要約や親の見解を
  混ぜない。
- 派遣手段が利用できない、または完了が確認できない場合は、レビューを
  親文脈で模擬せず停止し、その旨をユーザーに報告する。

### 7.3 L2 への設計上の対処

レビュー 001 は、v2 にはレビュアー側で指示ファイル注入を止める手段が
見当たらないと指摘する。本設計は次の運用を標準手順として組み込む。

- レビュー実行は、対象文書を使い捨てのクリーンなプロジェクト
  （AGENTS.md を置かない）にコピーしてから行うことを標準手順とする。
  ただしプロジェクトのクリーン化だけではグローバル AGENTS.md の注入は
  止まらない。そのため、標準手順には専用プロファイル（XDG 分離等で
  グローバル指示を持たない構成）での起動を含め、グローバル注入を
  無効化できる手段があるかを Phase 0 で検証する。手段が無い場合、
  L2 の「未達」は常態として扱い、§10 の支持表記に反映する。
- 作業プロジェクトで直接レビューする場合、L2 は「未達（既知の漏洩）」と
  記録し、支持表記は §10 の限定文言に従う。
- 注入の有無は §7.4 の証跡でケースごとに判定し、プロンプト上の指示
  （「渡されたもの以外を読むな」）を証跡の代わりにしない。

### 7.4 分離の検証（ポジティブ証跡）

マーカー不在だけを証跡としない（上流 verifier の制限事項と同旨）。
次を必須の証跡とする。

- マーカーテスト: 親会話にだけランダムマーカー文字列を置き、子の文脈
  （セッション export）と出力に現れないことを確認する（L1）。
- 指示ファイルマーカーテスト: 指示ファイルにだけマーカーを置くテストを
  別ケースとして実行し、結果を L1 と分けて報告する（L2）。
- トレース突き合わせ: 親の実行記録と子のセッション export を照合し、
  新規派遣であること、親子セッション ID の対応、レビュアー種別、
  必須パスの read 完了、ツール呼び出しのセッション帰属、結果の対応を
  検査する（D5 の範囲で v2 版 verifier を実装する）。失敗の判定は
  上流 verifier の条件（開始・完了・時刻窓・必須 read・最終応答の一致）
  に揃える。
- 実効権限の保存: §6.4 の実効権限ダンプを実行記録と一緒に保存する。
- 候補 (b) の場合の等価証跡: セッション export が存在しないため、呼び出し側で
  次を保存し、(b) 用 verifier で照合する。(1) リクエスト全文（ベース
  セッション ID、プロンプト、指定エージェント／モデル）とレスポンス全文、
  (2) ツール呼び出しのログ（呼び出し帰属、必須 read の完了）、
  (3) 保存物の SHA-256。(a) の突き合わせ項目（新規派遣であること、
  レビュアー種別、必須 read、結果の対応）と同等の合否判定を定義し、
  §10 の支持条件では (b) でも同等の証跡を必須とする。

## 8. ワークフロー対応

- brainstorm: レビュアー 7 名の派遣→プライマリが `concepts_brief.md` に
  合成→人間承認。
- draft: 承認済み brief を入力に起草。起草前の brainstorm 完了を前提条件として
  チェックする。
- review: 正典の 5 フェーズを順に実行し、各ステージの報告ファイルを
  書き出してから次へ進む。Step 8 の前に `zoom_out_report.md` の存在を
  確認し、なければ停止する。全フェーズを通すと派遣は最大で 15 回程度に
  なる（子セッション数として。上流の Muse 実績と同規模）。
- review-loop / resolve / drift-report / bootstrap: スキルとしては発見可能に
  するが、委譲を伴う部分はレビュアー 8 名の範囲に限る。範囲外の委譲が
  必要になったら停止する（N4）。

コストと上限: レビュー 1 回は子セッション派遣が多く、トークン消費と
所要時間がかかる。エージェント定義には v2 の `steps` 上限に相当する
指定があればレビュアー側に上限を設け、検証記録には派遣回数と使用
モデルを残す。具体値は Phase 3 の実測で決める。上限指定が v2 に無い
場合は、手順側で派遣回数の上限を定めて運用する。

## 9. モデル方針

- アダプタはモデルを固定しない。エージェント定義にモデル指定を持たせず、
  利用者の OpenCode 設定と起動時指定に従う。
- 検証記録には使用モデル識別子を必ず残す（F6 の記録項目）。
- 本リポジトリの開発検証では、当面 `opencode-go/crouton-alpha-free` を
  標準の検証モデルとする（利用者の決定、2026-11-09）。これは検証用
  プロファイルの既定値であり、生成物には埋め込まない。

## 10. 検証計画と支持主張の条件

### 層 1: オフライン検査（モデル呼び出しなし）

- 生成の再現性: 同じ入力から同じ生成物（ハッシュ一致）。
- 上書き拒否、パス検証（特殊文字、`.env.`、シンボリックリンク宛先、
  ソースツリー内生成）の単体テスト。
- 生成物の静的検査: 設定ファイルのパース、スキル配置の実在と ID の一致、
  コマンド定義の参照先、§6.4 の実効ルール列の順序検査。
- `debug agents` で EGM エージェント（プライマリ 1＋レビュアー 8）の
  実効権限ダンプを取得し、想定リストと突き合わせる。

### 層 2: ネイティブプローブ（スクリプト化モデル）

- v2 がスクリプト化されたローカルモデルで駆動できる場合に限り実施する。
  子セッション派遣の成立、親マーカーの不在、`.env` 読み取り拒否を
  モデル挙動に依存しない形で確認する。実施できない場合はその旨を記録し、
  層 3 の証跡で代替範囲を明示する。

### 層 3: ライブ検証（実モデル、人間承認つき）

1. 候補スナップショット SHA、生成物ハッシュ、ホストバージョン、モデル
   識別子、実行面（TUI/CLI）、日付を記録する。
2. /egm-brainstorm、/egm-draft、/egm-review を実際に走らせ、人間承認で
   一度止まることを確認する（`--auto` は使わない、F2）。
3. レビュアーの開始・完了・必須 read・成果物ファイルを証跡として残す。
4. 使い捨てファイルへの書き込み拒否を実地に確認し、子の有効権限を検査する。
5. §7.4 のマーカーテスト（L1、L2）を実施する。
6. 導入・ワークフロー・分離の結果を分けて報告し、欠けた証跡は「未検証」と
   明記する。

### 支持主張の条件

README 等で「OpenCode v2 対応」と書けるのは次のすべてを満たす場合に限る。

- 層 1 と層 3 が完了し、L1 の分離証跡（§7.4）が得られている。
- ハーネス文書（README の導入手順・対応表・検証状況・既知の制限）が
  更新されている。
- 上流のテストシナリオ（brainstorm/draft/review のシナリオ資産）を
  再利用または準用し、その結果を検証記録として公開している。
- 支持文はテスト済みのホストバージョン／モデル／実行面に限定して書く。
- 支持表記の主見出しは L2 の成否で切り替える。L2 達成時は
  「OpenCode v2 対応（分離検証済み）」、未達時は無条件の「対応」とは書かず
  「OpenCode v2 対応（親ターンの分離のみ検証済み。ホスト指示ファイルの
  レビュアー文脈への混入は既知の制限）」の形に限定する。

## 11. 実装フェーズ

- Phase 0（スパイク）: D1–D7 を実測する使い捨て実験。各項目に関門条件を置く。
  - D1 不成立（候補 (a)(b) のいずれでも §7.2 の不変条件と完了待ちを満たせない）:
    方式を根本から見直し、支持主張を行わない。
  - D2 不成立（読み取り専用を権限で表現できない）: D7 の結果と合わせて
    判断し、表現できなければアダプタの提供を見送る。
  - D3 不成立（登録経路が無い）: 配置可能な経路（ファイル配置）に限定して
    再設計する。
  - D4 不成立（探索される場所への配置経路が無い）: 方式 A は取り下げ、
    方式 B/C への移行を検討する。
  - D5 不成立（トレースが不足）: verifier の代替証跡（セッション export の
    範囲での検査＋層 3 の目視記録）を定義する。ただし §10 の証跡要件は
    引き下げない。代替証跡で §10 を満たせない場合は支持主張を行わない。
  - D6/D7: 確認のみ。結果は §6.4/§6.5 の確定に使う。
- Phase 1（最小実装）: 生成器と生成物（§6.3）、単体テスト、オフライン検査。
- Phase 2（検証ハーネス）: プローブと verifier（§10 層 2・層 3 の道具）。
- Phase 3（ライブ検証と文書）: 実モデルでの E2E、分離検証、README と
  導入手順、検証記録の公開。

## 12. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| v2 のサブエージェント派遣が新規セッションを保証しない | Goldfish の前提が崩れる | Phase 0 で最初に確認。保証できなければ方式 B/C を含め再設計し、支持主張をしない |
| 指示ファイルが子文脈に自動注入される（F7 の他ハーネス事例、v2 でも同様の指摘あり） | レビューの独立性が下がる | §7.3 のクリーン環境手順を標準化し、L2 を分離検証。未達なら支持表記に制限を明記する |
| 権限が設定通り強制されない／マージで上書きされる | レビュアーが書き込み等を行う、deny が無効化される | §6.5 の起動前検査で実効権限を照合し、不一致なら起動拒否。層 2/3 で実地確認するまで「読み取り専用」と主張しない |
| 設定のマージで利用者設定が生成設定を汚染する | 再現性が失われる | クリーンなプロファイルと使い捨てプロジェクトで検証する（XDG 分離だけでは不十分だった V1 の知見を踏襲）。有効設定を debug で毎回検査する |
| 上流 EGM が更新されスナップショットが陳腐化する | 正典との乖離 | vendor スナップショットに取得元コミットとハッシュを記録し、更新は差分レビューを伴う明示手順にする |
| コマンド引数の事前評価（シェルマーカー展開）で未信頼テキストが実行される | V1 で注意喚起された既知の問題 | §6.6 の規約（引数は絶対パスのみ、マーカー検出で停止、素材はファイル経由）を生成物と手順に落とし込む |
| レビューの実行コスト（派遣回数・トークン）が大きい | 利用者の費用と時間が膨らむ | §8 の通り steps 上限の検討と、検証記録への派遣回数・モデルの明記。安価な検証モデルでの事前確認を手順に含める |
| 候補 (b) のベースセッション汚染・非永続化の未検証・権限／証跡の欠落 | 見かけ上分離したレビューが実際は汚染されている | §7.2 の派遣ごと新規作成を原則化し、D1 (i)–(iv) の実測を関門とする。不成立なら (b) を採用せず、(b) 経路での支持主張も行わない |
